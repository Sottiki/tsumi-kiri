最終更新：2026-11-25
状態：**確定**（変更の履歴は Git に残す）

実装の段階と、それぞれの完了条件。PR は下の「進み具合」の表の1行ごとに1つ作る。

段階の進め方（計画 → 実装 → 確認、PR の書き方、ドキュメントの見直し）は、CLAUDE.md の「段階の進め方」に従う。

画面の段階（4・6・9A）の「画面案と並べて見比べる」は人が見る項目。段階4・6は、Claude が Playwright MCP でスクショを撮って画面案と比べ、最後にユーザーが確認する。スクショは Google Fonts を読み込まずシステムの書体になるので、書体は見比べの対象にしない。段階9A は、作ったファイルをユーザーが Excel で開いて画面案②と比べる。

参照：仕様は SPEC.md、見た目は DESIGN.md、作り方は docs/architecture.md、検証例は docs/test-cases.md。

段階1〜3は画面のない部分（計算とデータ）、段階4〜9は画面、段階10は公開。

**並行の決まり**
- 「始められる時期」に書いた段階が終わる（PR がマージされる）までは、その段階を始めない
- 前提がそろった段階どうしは、並行に進めてよい。並行するときは別のブランチ・別の PR にする
  - 残りの段階で並行しうるのは、10A（公開の仕組み）と、7・8 のどちらか。10A はアプリのコード（`src/`）に触れないので、ほかの段階と重ならない
- 並行の PR は、触るファイルが重ならないようにする
- 並行中に型（`core/types.ts`）を変える必要が出たら、先に止めてユーザーに確認する。型を変えると、並行しているほかの PR にも影響するため
- 画面の段階（4〜8）は同じ部品を触るので、並行にしない

**並行中のドキュメントの扱い**

- 実装役は、仕様や設計で迷ったら、ユーザーに直接聞いて決める。確認を取るまで実装しない。
- 決まったことは、実装役がその場で、自分の PR の中でドキュメント（SPEC.md・DESIGN.md・docs/architecture.md・docs/test-cases.md・tasks.md）に書く。自分の段階に関わる範囲だけを直す
- もう一方の段階にも関わる決定（`core/types.ts` の既存の型の変更、両方が使う関数の動きの変更など）は、作業を止めてユーザーに確認し、もう一方のセッションにも知らせる
- SPEC.md「8. 決定事項」の番号は、並行の PR どうしでぶつかることがある。後からマージする側が、`git fetch && git rebase origin/main` のときに番号を振り直す。PR を出す直前にも取り込む
- 「進み具合」の表の「状態」は、それぞれの実装役が自分の PR で「完了」にする
